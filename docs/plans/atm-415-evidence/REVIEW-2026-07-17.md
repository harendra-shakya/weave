Root causes:
1. `validate-contracts.mjs walkFiles()` recurses `.next/` and `node_modules/` with no exclusion → 9 framework false positives.
2. The scanner is a naive substring/word-boundary match that cannot distinguish token **mention/negation** from **use**. A chainless app *should* be able to tell users "no custody" and its eval proof *should* be able to name what it checked for — both trip the scan.

Where the "0 tokens" claim actually came from: the passing narrow scans — the negative test's **spec-only** scan (`nft-storefront.spec.json` is genuinely token-free) and the dependency check — generalized in prose to "39 files".

Recommended fix (handed to owner; **not applied**):
- Low-risk, in `tools/` (not frozen): exclude `.next`/`node_modules`/`.git` from `walkFiles`. Removes 9 false failures. (Alone this does not green the gate.)
- The remaining 6 require either excluding `proof/` eval artifacts from the token scan, or a negation/allowlist mechanism. Banning the literal words `custody`/`chain` is what causes the false positives, and the token list lives in **frozen** `contracts/negative/nft-chainless-contract.json` (`37dff0b…` in freeze-digests). Changing it is an **OWNER_GATE** stop — recorded, not worked around.

Substantive conclusion: **the app is actually chainless** — no chain dependencies, no chain-integration code; every forbidden-token occurrence is a negated disclaimer or the scanner's own list echoed in proofs. The defect is in the *proof tooling and the claim's wording*, not the boundary. Honest restatement used in the ATM-419 Linear comment.

### 2B-3 — Two user modes

Written (Artifact A): `packages/weave-tool/skills/weave-guided-intake/SKILL.md`,
registered in `REQUIRED_SKILLS` (package validates at 12 skills).

**Two-mode contract (Artifact B):**

- **MODE A — Loop (existing).** Owner gives intent; `lifecycle-runner.mjs`
  advances stages autonomously with no inter-stage prompting. For experienced
  users and repeat iteration cycles. This is what exists today.

- **MODE B — Guided (new).** `"mode": "guided"` in `lifecycle-state.json`. At the
  start of each stage the runner prepends the stage's assigned skills from
  `skill-registry.json` as a grill/extraction prompt before any work. The owner is
  depth-extracted at every gate. Full flow:

  Shallow prompt → **[PRE-INTENT]** `brand-ideation` + `grill-me` (brand vision,
  one exact customer, visual direction) → **[INTENT]** `grill-me` (problem, 90-day
  success criteria, non-goals) → `intake.json` auto-populates `intent.json` →
  **[RESEARCH]** `grill-with-docs` + market questions → **[SELECTION]**
  `design-an-interface` (visual direction) + IA questions → **[PLAN]** `prototype`
  (lo-fi) → owner reviews → `to-prd` (full spec) → **[ENGINEERING]**
  `frontend-component-build` + `tdd` + `accessibility-audit` → **[QA]** `qa` +
  `impeccable` + `security-review` → **[KPI]** `analytics-strategy` →
  **[MARKETING]** `landing-page-copy` + `email-sequences`.

  End state: a person who types "I want to build something for dog owners" exits
  guided mode with a production-grade app — real design tokens, accessible
  components, converting copy, and a KPI baseline — without knowing what any of
  those words meant at the start.

  Implementation path (minimal, no runner rewrite):
  1. Add `"mode": "loop" | "guided"` to the `lifecycle-state.json` template.
  2. In `lifecycle-runner.mjs`: in guided mode, prepend each stage prompt with the
     relevant grill invocation + phase question set from `skill-registry.json`.
  3. Add `weave-guided-intake` (done — Artifact A).
  4. Register `weave-guided-intake` in the package skill set (done — validates at 12).

  What a normal user can now do that they couldn't before: start from a one-line
  prompt and be carried through brand, design, build, QA, and measurement with the
  depth extracted for them at each gate — instead of the loop's single up-front
  intent hand-off that assumes the owner already knows what to specify.
