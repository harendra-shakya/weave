### Bug found and fixed (root cause, not symptom)

Live interaction surfaced a genuine correctness bug invisible to the existing 100%-passing QA gate: the very first declined payment reported "the single bounded retry has already been used," before any retry was ever attempted — contradicting the frozen `contracts/state-transitions.json` `retry_rule` ("budget consumed only if the retry itself fails"). Root cause: `checkout.authorize()` hardcoded `isRetry: true` on every decline, including the original attempt, not only the actual retry call.

Fixed at the shared function (not the page): `apps/video-storefront/src/lib/engine/checkout.mjs` now takes `isRetryAttempt` (default `false`); `apps/video-storefront/src/lib/store.mjs`'s `retryPurchase()` is the only caller that passes `true`. Updated `apps/video-storefront/tests/engine.test.mjs` (the old test encoded the buggy behavior as expected; added two tests for the actual retry_rule and fixed the exhaustion test). Full suite: **49/49 pass** (`npm test` from `weave-v5-apps` root). Re-verified live in the browser: first decline -> "one bounded retry is available" -> retry with a valid token succeeds -> second decline (fresh order) -> correctly reports the retry as spent.

### Adaptation loop (ATM-417 product-learning loop)

- Diagnosis traced the cohort-runner mechanism (`tools/cohort-runner.mjs` + `packages/commerce-core/cohort.mjs`): funnel branch probabilities are hardcoded constants, independent of any app-readable state, and checkout is always authorized with a fixed token in cohort runs (the decline/retry path above is never exercised by cohort runs). Consequence: `conversion_rate` and `fulfillment_success_rate` are structurally invariant to any single-app bounded change this cycle; only `aov`/`gross_revenue` are reachable, because the runner reads each order's price from the app's own catalog fixture.
- Ranked 4 candidates by evidence/impact/effort/risk (full table in `apps/video-storefront/proof/adaptation/adaptation-report.json`); selected a ~10% catalog price adjustment (bounded, single-file, zero frozen-contract or cross-app surface touched — verified `catalog.json` is absent from `contracts/freeze-digests.json`).
- Retest: identical seed `atm417-baseline-v1`, run twice, ledger digest byte-identical to both each other and the pre-adaptation baseline (expected — price isn't part of the event stream, only the KPI computation). Before/after: `aov` $20.51 -> $22.54 (+9.93%, target "flat or improved" **met**), `conversion_rate` and `fulfillment_success_rate` unchanged (targets not met, but structurally unreachable this cycle — not a failed adaptation). All four guardrails held.
- **Decision: ITERATE.** Next recommended change (recorded for ATM-420, not implemented here — out of ATM-417's bounded scope): extend `commerce-core/cohort.mjs` to read optional per-app elasticity parameters from each app's frozen spec, so a future bounded adaptation can legitimately move conversion/fulfillment KPIs.
- Operational note: the catalog fixture is memoized per-process in `catalog.mjs`; a fixture edit needs a dev-server restart to appear in the live UI (confirmed: stale prices before restart, correct after).
